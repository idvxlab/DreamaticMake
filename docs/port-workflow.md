# 端口式工作流与独立预览

本版将原来的阶段卡片网格替换为可平移、缩放、拖动的端口画布。节点处理数据，左右端口交接真实输入输出；旁边的预览区展示数据内容。拖动只保存该浏览器的布局，不改变业务连接。连接由统筹者与服务端契约维护。

## 本次启用的流程

1. **原始需求**：用户创建项目时的原文，作为第一个输入。
2. **需求分析**：澄清用户目标、场景、偏好；输出 `requirementCards`。第一阶段当前角色版本保留，运行时增加了可选的结构化输出说明。
3. **意图理解 / 功能拆解**：使用独立的 `.pi/stages/intent-analyst.md`，输出 `functionModules`。每个功能明确需求引用、输入、输出、验收和实现类型，不能指定硬件型号。
4. **硬件选型**：消费功能模块，检索已有元件库和官方来源，提出精确器件组合。原 Arduino 官方资料、STEP 检查、来源关联与几何审批约束继续生效。
5. **统筹连接**：硬件作者提交后，统筹者通过 `workflow_route` 明确每个功能与器件的关系；随后才进行独立审阅。一个功能可使用多个器件，一个器件可回应多个功能。映射本身不构成几何、电气或实物验证。

每个新功能必须引用真实需求端口；每项需求需要有功能覆盖。每个被选器件必须回应功能；每个功能需要连接、纯软件解释或明确的未解决原因。硬件/混合功能不能以“纯软件”绕过选型。未解决项或失效连接不能通过服务端确认校验。

映射保存源版本键、需求/功能/硬件版本、器件来源引用和来源产物哈希。功能、需求、硬件草稿或来源产物变化后，原映射失效，必须重新统筹。库更新不会悄悄改写项目的来源版本。

## 返回上游

意图或硬件阶段缺少真正的上游输入时，可调用 `workflow_request_upstream`，指定目标节点、原因和需要补充的内容。当前链停止，目标及下游版本失效；系统重新调度目标节点，原有确认记录保留。补充后的版本仍须独立审阅与用户确认，不能自动批准。短时间内的重复回退有次数限制，已有同目标待处理请求也不能反复创建。

这不是网络、模型故障的通用恢复方式，也不能用于消除尚无证据的硬件约束。资料和模型检查仍由原有工具负责。

## 预览区

- 卡片：原始需求、需求卡、功能模块及其输入输出，问题卡和确认操作。
- 连接：逐功能展示其硬件响应、角色与理由，以及上游补充请求；点击连线可以检查原因。
- 器件：目录参数、商品/官方链接、安装几何状态、来源 candidateId/rawHash。可进入实时资料库浏览参数、文档与 STEP。
- 模型：已有 CAD 网格可以预览；没有模型时显示空状态，不将默认参数外壳伪装为产品结果。

布局与视口保存在该项目的浏览器本地存储。问题与确认组件始终只挂载一份。

## 外观、结构与 CAD 的待确认草案

画布下方列出了拟议分工，虚线仅表示待确认的接口草案：

| 节点 | 拟议输入 | 拟议输出 |
| --- | --- | --- |
| 外观 | 用户需求、操作布局、器件约束 | 形态与外观方案 |
| 结构 | 外观、硬件包络、接口和安装需求 | 装配关系、安装、开孔与走线约束 |
| CAD | 已确认外观与结构、准确硬件几何 | 工程模型与检查报告 |

本次新流程只启用到硬件选型，`productFlow.enabledThrough = hardware`。确认硬件后不自动运行后续作者；运行时也会拒绝对该流程启动后续阶段。原有工程工具没有被重写。这些草案等待用户确认与进一步细化。

## 兼容与备份

旧版需求保留原文摘要，作为单个需求输出；不把旧 facts 猜成功能模块。旧版意图缺少 `functionModules` 时，界面明确提示，重新运行意图阶段后才生成真正的功能端口。没有模块时不能把旧文字当成有效的新硬件连接。旧项目数据不在部署时自动改写。
